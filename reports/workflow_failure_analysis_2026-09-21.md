# 工作流异常分析报告

日期：2026-09-21  
对象：AuTo_LaTeX `run_workflow` 多阶段执行链  
事故工作流：`bbb7e35b-9ac3-4d53-97c7-72b1460e752b`（`wf-task-4`）

## 1. 摘要

本次异常不是单一模型输出质量问题，而是工作流控制层的复合故障：Agent 的步骤预算被硬编码扩大、模型请求异常无熔断重试、阶段专属任务在调度时丢失、外层超时取消未被持久化层捕获。四者共同造成了大量 API 请求、阶段无法收敛、最终记录永久停留在 `running`。

## 2. 事实与时间线

SQLite 记录显示：

- 10:04:49：工作流启动，状态为 `running`。
- 10:04:49：`stage-0-mathwrite` 启动。
- 10:08:34：写作阶段完成，耗时约 225 秒；LaTeX 及编译辅助文件已登记为产物。
- 10:08:34：`stage-1-math` 启动。
- 此后该阶段没有 `finished_at`、`result` 或 `error`，工作流也没有更新终态。
- 调查时系统中已不存在 Python 执行进程，因此数据库中的 `running` 是遗留状态，不代表任务仍在运行。

## 3. 根因

### 3.1 直接原因：步骤上限被无条件改成 20

`Agent.run_agent` 读取 `runtime.agent_max_steps=5` 后，又执行 `max_step = 20`。配置和调用者显式传入的限制全部失效。一个无法收敛的阶段因此最多可进行 20 轮模型请求。

### 3.2 请求异常会持续重试

模型 API 异常原先仅打印错误并 `continue`。系统没有连续失败计数、退避和熔断，也不把错误写入工作流记录。持续性网络、限流、服务端或请求格式错误都会重复消耗请求，直到步骤预算耗尽或工作流总超时。

### 3.3 Stage 的专属任务被调度器丢弃

`stage_tasks` 中每个阶段包含 `expert` 和 `task`，但构造 `Stage` 时只保留了专家和工具权限。执行阶段时又统一使用整个工作流的 `goal` 创建上下文。

后果是：

- 产出阶段不知道自己的精确产出要求；
- 验收阶段收不到独立复核指令和停止条件；
- 不同阶段被退化成对同一宽泛目标的重复处理；
- 第二阶段更容易重复读取、分析或调用工具，无法按验收条件及时结束。

### 3.4 外层超时早于内部最坏执行时间

整个工作流的工具超时为 600 秒，覆盖全部阶段。第一阶段已经消耗约 225 秒，第二阶段只剩约 375 秒。与此同时，内部 Agent 最多允许 20 轮，每次模型请求自身还可能等待 60 秒。内外预算不一致，使外层取消成为可预期结果。

### 3.5 取消没有落库

外层 `asyncio.wait_for` 超时时会取消内部协程并抛出 `asyncio.CancelledError`。当前 Python 中它继承自 `BaseException`，而原工作流只捕获 `Exception`。因此取消绕过了阶段和工作流的失败收口逻辑，造成数据库永久残留 `running`。

## 4. 放大因素

- Agent 达到步骤上限时返回 `None`，调用方再把它转换为空字符串；如果没有先触发外层超时，这种失败可能被误记为成功。
- “独立验收阶段”的规划校验只要求任意阶段包含验收关键词，没有要求它位于产出阶段之后。
- 原允许验收的专家列表不包含 `math`，与本次使用 Math 专家做独立数学复核的实际需求不一致。
- 子 Agent 的逐轮模型请求和异常没有持久化审计记录，因此可以从控制流和数据库终态确认故障链，但无法从本地数据库精确还原每一次供应商 API 响应。

## 5. 根因结论

主要故障链为：

`Stage 指令丢失` → 专家无法按阶段目标收敛 → `20 轮硬编码及异常无熔断` → API 请求数量放大 → `600 秒外层超时取消` → `CancelledError 未捕获` → 工作流未完成且记录永久显示 `running`。

该故障属于控制平面缺陷，不能通过单纯更换提示词或提高工作流超时时间可靠解决。
